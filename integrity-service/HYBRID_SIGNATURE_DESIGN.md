# Hybrid Dual-Signature Scheme: Architecture & Design

## 1. Executive Summary & Design Rationale

The CryptoScan platform enforces a **production-grade hybrid dual-signature scheme** combining classical cryptography with post-quantum cryptography:

* **Classical Component**: **ECDSA** over curve **secp256k1** (reusing the existing Ethereum-compatible wallet infrastructure).
* **Post-Quantum Component**: **ML-DSA-65** (Module-Lattice-Based Digital Signature Algorithm, specified in **NIST FIPS 204**).

### Why Hybrid?
Classical public-key cryptography (RSA, ECDSA, Ed25519) is vulnerable to Shor's algorithm running on a cryptographically relevant quantum computer (CRQC). However, emerging post-quantum algorithms have less real-world battle-testing. A hybrid dual-signature ensures that:
1. **Immediate Compliance**: Existing classical verifiers (e.g. EVM smart contracts, existing PKI) continue to verify the ECDSA signature without breaking.
2. **Quantum Resistance**: The post-quantum signature provides forward security designed to provide resistance against quantum-capable adversaries attempting retrospective forgery or future signature invalidation.
3. **Dual Security Requirement**: Verification requires **both** signatures to be valid. A compromise of either algorithm alone is insufficient to forge a valid hybrid signature.

> **Terminology Note**: This design does not claim to be "quantum-proof." Instead, it is accurately described as a **post-quantum cryptographic signature designed to provide resistance against quantum-capable adversaries**.

## 2. Environment & Runtime Prerequisites

* **Node.js Runtime Requirement**: **Node.js v24.7.0 or higher** (verified and running on **Node.js v24.13.0**).
* **Cryptographic Engine**: Native **OpenSSL 3.5.4+** embedded directly within the Node.js executable.
* **Zero Native Toolchains**: Uses Node.js built-in `node:crypto` with native `ml-dsa-65` support. Requires no `liboqs`, no `pqclean`, no `node-gyp`, and no external C/C++ compilers.

---

## 3. Cryptographic Key Separation

Complete isolation is enforced between the classical and post-quantum keys:

1. **Independent Key Material**:
   - The ECDSA private key is managed strictly through [`integrity-service/kms.js`](file:///c:/Users/Shravani/Downloads/Cryptoscan-main/integrity-service/kms.js).
   - The ML-DSA-65 keypair is generated independently using `crypto.generateKeyPairSync('ml-dsa-65')`.
   - **Zero Cross-Derivation**: ML-DSA keys are never derived from, hashed from, or coupled to the Ethereum private key.
2. **Secret Protection**:
   - The ML-DSA private key is never returned in signature results, never serialized into JSON, and never printed in logs.
   - PQC public keys are identified by a deterministic public key fingerprint (`pqcKeyId`).

---

## 4. Domain Separation

To prevent signature replay attacks across different applications or protocol boundaries, all messages are framed within an explicit domain-separated context:

```text
Domain Tag: "CryptoScan-Integrity-v1"
Signed Byte Sequence: "CryptoScan-Integrity-v1\n" || rawMessageBytes
```

* **Deterministic Payload**: Both the classical ECDSA signature and the post-quantum ML-DSA signature authenticate the exact same domain-separated byte sequence.
* **Collision Resistance**: Any signature produced in this context cannot be replayed as a raw document signature or transaction elsewhere.

## 5. Output Format

Hybrid signing returns a standardized, self-describing payload:

```json
{
  "algorithm": "ECDSA-secp256k1+ML-DSA-65",
  "classicalSig": "0x4f3e... (65-byte hex string)",
  "pqcSig": "base64-encoded-string (3,309 bytes decoded)",
  "pqcKeyId": "pqc-mldsa65-a1b2c3d4e5f60718"
}
```

### Fields:
* **`algorithm`**: Exact identifier string `ECDSA-secp256k1+ML-DSA-65`.
* **`classicalSig`**: 65-byte ECDSA signature (`r, s, v`) generated by the KMS-managed Ethereum wallet.
* **`pqcSig`**: Base64-encoded FIPS 204 ML-DSA-65 signature (exact length: 3,309 bytes).
* **`pqcKeyId`**: Opaque non-secret key identifier derived from the SHA-256 digest of the ML-DSA public key's SPKI DER representation.

## 6. Signing & Verification Workflows

### Signing Flow: `signHybrid(message, options)`
```text
Input Message (Buffer / String)
         |
         v
[ Prepare Message ] ---> Prepends "CryptoScan-Integrity-v1\n"
         |
         +---------------------------------------+
         |                                       |
         v                                       v
[ Classical Signer ]                    [ PQC Signer ]
KMS getSigningKey()                     Native node:crypto ML-DSA-65
ethers.Wallet.signMessage()             crypto.sign(null, prepared, pqcPrivKey)
         |                                       |
         v (0x... hex)                           v (3,309 bytes base64)
    classicalSig                                pqcSig
         |                                       |
         +-------------------+-------------------+
                             |
                             v
               Hybrid Signature Object
```

### Verification Flow: `verifyHybrid(message, hybridSignature, options)`
```text
Hybrid Signature Object + Message
         |
         +--> Check algorithm === "ECDSA-secp256k1+ML-DSA-65" (reject if mismatch)
         |
         +--> Prepare message with "CryptoScan-Integrity-v1\n"
         |
         +--> Step 1: Classical Verification
         |    ethers.verifyMessage(preparedMessage, classicalSig)
         |    Matches expected Ethereum address? -> classicalValid (true/false)
         |
         +--> Step 2: Post-Quantum Verification
         |    Resolve ML-DSA public key from registry via pqcKeyId OR options.pqcPublicKey
         |    crypto.verify(null, preparedMessage, pqcPublicKey, pqcSigBuffer)
         |    Signature valid? -> pqcValid (true/false)
         |
         v
Overall Valid = (classicalValid === true && pqcValid === true)
```

> **Strict Conjunction**: If either signature fails verification, is tampered with, or is missing, `valid` is strictly `false`. Partial validity is never treated as successful verification.

## 7. Future KMS and HSM Integration

In cloud and hardware production environments:
* **Classical Key**: Backed by AWS KMS (`secp256k1` asymmetric key) or Azure Key Vault HSM.
* **Post-Quantum Key**: Backed by next-generation Cloud KMS or Hardware Security Modules supporting FIPS 204.
* **Interface Transparency**: Consumers of `signHybrid()` and `verifyHybrid()` interact with the same public contract regardless of whether keys are stored in memory or in a dedicated HSM.
